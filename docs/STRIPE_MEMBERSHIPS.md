# Stripe web memberships

Implemented locally on 2026-10-15. This changes web membership checkout and account management. It does not recreate existing subscriptions, move billing dates, change App Store purchase APIs, or protect/change media URLs.

## Application flow

- Pricing and checkout keep the existing PianoLIT layout. Trial eligibility is calculated on the server; returning subscribers are shown a paid start. Local prices must match the selected account's active USD Stripe Price, amount and interval before a subscription is created.
- The membership card form uses Stripe.js Card Element, SetupIntents and PaymentIntents. PAN/CVC never pass through PianoLIT. A newly entered card requires a server-created SetupIntent that succeeded for the current operation and customer before it can authorize a subscription or card replacement. Returning checkout may instead use the stored membership PaymentMethod: the server checks the authenticated account’s saved-card reference, billing account, customer, card type and displayed brand/last four, and rechecks provider ownership at purchase. A client-supplied provider ID never selects the method. The subscription still uses `default_incomplete`, bank/PaymentIntent authentication and final server verification. The server retrieves it; posted IDs do not establish ownership.
- Checkout provisions a membership customer, independently of the shop customer. It creates a subscription with `default_incomplete`, an explicit default payment method, and an operation idempotency key. The browser completes any invoice/bank authentication, then asks the server to retrieve and confirm the subscription. Confirmed active/trialing checkouts return to Discover with a one-time, account-owned success modal. Its summary shows the saved plan/status, the verified current subscription's purchase date, the next charge and trial end when applicable. Verified date snapshots are bound to that subscription, so resubscribing never displays the original membership record's creation date; scheduled cancellation suppresses the next charge.
- Card replacement sets the subscription's verified payment method and, for a PianoLIT-owned plan schedule, its future default. It never deletes the previous card first or edits a different shop customer. Updating a card does not silently charge an outstanding invoice; the user uses the Stripe-hosted invoice's Pay/View link to complete payment.
- Every Stripe membership with a saved card can explicitly remove it from Billing through a confirmation dialog, including active, trial and grace-period memberships. The dialog explains that removal does not cancel membership and another card is needed before a future payment to avoid failure/interrupted access. The server binds removal to the authenticated account, saved-card reference and exact provider target, and rejects shared/foreign customers or unrelated live subscriptions; a legacy subscription without a stored ID must have at most one live candidate. The verified target is committed before the provider mutation, so retries cannot select a changed default or delete a replacement card. Modern cards use [PaymentMethod detachment](https://docs.stripe.com/api/payment_methods/detach?api-version=2025-03-31.basil); legacy cards use scoped [customer card deletion](https://docs.stripe.com/api/cards/delete) or [Source detachment](https://docs.stripe.com/api/sources/detach). Both legacy response shapes are supported. Only that card is removed: the membership/customer, subscription status/dates, payments and invoices remain intact. Existing provider reconciliation remains authoritative for subsequent payment outcomes. No card is removed merely by opening or dismissing the dialog.
- Changes between monthly/yearly plans are scheduled at the existing billing-period boundary with no current-period proration. The current plan remains displayed until the change happens. Existing discount IDs and supported tax/default settings are retained. Selecting the current plan removes the pending change. Complex item discounts, multiple subscription items or external schedules require billing review rather than an automatic rewrite.
- Cancel schedules an end at the existing period boundary (an unpaid incomplete checkout is canceled immediately without a new invoice or proration), updates the full returned state and releases a PianoLIT-owned pending plan change. Resume withdraws scheduled cancellation. Both preserve the existing access policy, including trial/grace access and the unconditional super-user override.
- Pause/unpause are explicit desired states, not a toggle. Pause uses `pause_collection.behavior=void`, preserves the billing calendar, suspends ordinary web Premium media immediately and carries no unused paid time forward. An open unpaid invoice blocks pause. Cancellation, renewal, pause and content access are separate states; existing mobile status methods remain unchanged.
- Invoice history loads when its tab opens, with 12 rows per Stripe page, older-page navigation, escaped output and a recoverable failure state. Opening My Membership itself does not call Stripe for invoice history. Ended subscriptions retain invoice access. Payment history is scoped to the authenticated membership customer across its old and new subscriptions, so resubscribing does not hide earlier invoices. Settings links accounts with a membership record to My Membership even after it ends; an ended account can choose a new paid plan and reuse its saved card or enter a new one.

## Ownership, retries and local state

`app/Billing/Stripe` contains account selection, the isolated provider gateway, durable operations, normalized subscription state, membership checkout/management and webhook processing.

The additive migration adds exact subscription/account identity and payment/schedule metadata to `stripe_memberships`. New bookkeeping fields are hidden from the model's existing JSON serialization. Legacy records are linked lazily or during reconciliation only when Stripe returns one unambiguous current subscription (or one historical subscription when none is current). Multiple candidates require review; no first-subscription guessing is used.

`stripe_billing_profiles` stores each account's membership customer. `stripe_billing_operations` reserves purchase ownership across tabs and records provisioning/setup/subscription identities. Stable idempotency keys cover provider mutations. All membership mutations and refreshes serialize on the account row. Local writes roll back together; a provider subscription created before a local failure is recovered by its operation metadata. Mutating responses are followed by a current provider read, because an idempotent response can contain an older snapshot.

An unresolved subscription creation older than 23 hours is not blindly replayed: the operation's customer subscriptions are searched for its provider metadata first, and an unmatched old operation requires review. This avoids creating another subscription after Stripe can discard an idempotency key. Minimal operation identities are retained, rather than pruned and later mistaken for new requests.

Accounts still associated with Apple billing are blocked from purchasing a second billing source through the web. Existing Apple records, history and iOS contracts are retained. Switching such an account to web billing requires an explicit provider-transition workflow; this implementation does not silently replace its Apple membership. Multiple existing local membership rows also require review.

## Stripe accounts and API versions

The installed SDK is `stripe/stripe-php` **22.0.0**. It requires PHP 7.4 or later; the application already runs on PHP 8.3 locally. Only Stripe changed in the dependency lockfile. The pre-existing `teapot/status-code` PHP upper-bound mismatch remains a separate dependency issue; the local Stripe-only Composer update used `--ignore-platform-req=php+` rather than updating unrelated packages.

Membership requests use per-client credentials and the explicit **2025-03-31.basil** API contract. This version supports modern payment confirmation and item-level billing periods. The shop's existing static client keeps `STRIPE_VERSION`, falling back to `2020-03-02`; its token/source purchase flow is retained. Its legacy upcoming-invoice helper retains the legacy endpoint through an explicit raw SDK request. The application does not change the Stripe account-wide API version.

Configure these through server environment/configuration, never by exposing secrets in a page:

- `STRIPE_US_KEY`, `STRIPE_US_SECRET`: US publishable/secret API keys. The pre-existing `STRIPE_KEY`/`STRIPE_SECRET` remain US fallbacks.
- `STRIPE_SWISS_KEY`, `STRIPE_SWISS_SECRET`: Swiss account keys for existing Swiss memberships.
- `STRIPE_US_WEBHOOK_SECRET`, `STRIPE_SWISS_WEBHOOK_SECRET`: separate endpoint signing secrets. `STRIPE_WEBHOOK_SECRET` is the legacy **US-only** fallback. A Swiss endpoint needs its own signing secret.
- Optional `STRIPE_US_MONTHLY_PRICE`, `STRIPE_US_YEARLY_PRICE`, `STRIPE_SWISS_MONTHLY_PRICE`, `STRIPE_SWISS_YEARLY_PRICE`: Price IDs when they differ from the existing local Plan names (`monthly`/`yearly`). Changing these affects future selections; it does not replace existing subscribed prices.

For existing memberships, account selection uses the source's persisted account, then the explicitly verified exceptions in `memberships.stripe_accounts`, then the existing historical Swiss customer list. It never lets an unrelated shop customer choose the membership account. Verify old customer/account mappings before activation, particularly manually created or unlisted historical Swiss customers. The exception map is used only by the modern membership client; the shop/mobile jurisdiction helper and its historical list remain unchanged.

## Webhooks and reconciliation

The same `/webhooks/stripe` URL accepts **snapshot events** from both accounts. The raw body must pass signature verification with that account's secret and timestamp tolerance. The verified account, rather than posted identity, chooses provider credentials. Missing signing configuration fails closed. Valid unsupported event types receive 200 without side effects.

`WebhookProcessor::EVENTS` is the canonical list of 20 required subscriptions, customer/default-card updates, payment-method updates/detachment, successful/failed/action-required invoices, charges, refunds and disputes. Existing event selections can be edited in the Dashboard. Selecting an exact non-latest snapshot version such as `2025-03-31.basil` requires creating a replacement through the API; the application's explicit `stripe:webhook --account=us --create` command sets that version and event list. Creation enables the replacement immediately and gives it its own signing secret. The handler currently accepts one current secret per account: update the matching environment secret/configuration promptly, verify and resend any failed deliveries to the replacement, then disable the old destination once its outstanding events have successful deliveries. A successful replay proves signed delivery, not the entire checkout lifecycle. Do not create another endpoint just to edit its event selections. See [Stripe webhook versioning](https://docs.stripe.com/webhooks/versioning).

Handled event IDs are stored uniquely per billing account in `stripe_webhook_events`. The inbox retains only object identities and minimal accounting fields, not raw contact/address/card/authentication payloads. Processing reads current provider subscription state under the account lock instead of applying delayed snapshots. Events about a different subscription cannot overwrite the linked one. A failure retains the inbox entry, rolls back local processing and returns a failure so Stripe retries.

Charge recording is idempotent regardless of campaign-attribution settings. Minimal charge receipt markers remain durable; historical duplicate payment rows are not deleted or silently rewritten. Refund events refresh recorded refunded amounts. Dispute events refresh the associated charge; they do not introduce an automatic account ban or refund policy. Existing financial history is retained for excluded analytics accounts, while `Activity\ExcludedAccounts` continues to exclude their analytics collection.

`stripe:reconcile` replays pending inbox entries and rotates through the least recently synchronized memberships. It makes **read-only Stripe requests** and updates local state; it does not charge, cancel, create subscriptions, change provider data or send email. Completed inbox payloads older than 90 days are reduced to `{}` while their event identities remain for deduplication. The Laravel scheduler runs it hourly with overlap protection. Servers scheduling individual commands must add it explicitly.

`stripe:reconcile --audit` is read-only locally and remotely (no provider requests). It reports counts of ambiguous ownership, historical duplicate charges, missing subscription links, pending webhooks and old unfinished checkouts. It also lists unlinked source IDs, resolved US/Swiss account, customer ID, local status and existing/missing owner, bounded by `--limit` (100 by default). The resolved account is the configured lookup destination, not fresh provider verification. Resolve ambiguity using verified Stripe records; never choose a subscription from its list position.

As of 2026-10-19, ordinary hourly reconciliation treats several ended provider subscriptions as retained history when the local source is also `canceled` or `incomplete_expired`, has no subscription link and has no current/future renewal or membership-end date. Every returned subscription must have an ID, belong to the same customer and be `canceled` or `incomplete_expired`. The command prints `Historical membership left unlinked: source ...` with its account/customer and subscription IDs/statuses, advances the existing rotation, and leaves identity, status, dates, card, access and financial history untouched. This expected historical case does not increment the failure count or get reported to Bugsnag. It is **rechecked with fresh provider GET requests on every rotation**, rather than permanently ignored. One new live subscription can therefore be resolved normally; multiple live candidates, empty results, local/provider status conflicts, provider errors and pending-webhook errors remain failures. Targeted `--source` refreshes and web billing actions still reject ambiguous history.

Unresolved subscription errors now carry a minimal `stripe_membership` context in local logs/Bugsnag: source ID, billing account, customer ID, local status, subscription count and subscription IDs/statuses. The public exception message is unchanged; full provider responses, contact information and card data are not added. After deploying this PHP-only change, use `php artisan stripe:reconcile --audit` to identify the current local rows, then check the next scheduled reconciliation's historical lines and remaining errors. No migration or asset build is needed. Existing Bugsnag events remain as history; stopping new occurrences requires deployment.

`stripe:reconcile --source=119` refreshes only that Stripe membership source. It makes provider GET requests and updates the selected local membership/card state in the normal account transaction. It does not process/retry webhook entries, redact old inbox payloads or select unrelated sources. It rejects missing/invalid source IDs, a missing account owner, shared/changed ownership and multiple candidate subscriptions; failure rolls back the local refresh without advancing that source's synchronization timestamp. A bare `--source` is an error, not a global reconciliation. Do not combine `--source` and `--audit`. A successful targeted refresh prints the verified account and subscription ID. Ordinary hourly reconciliation retains its existing rotation/inbox behavior.

`stripe:webhook --account=us` (or `swiss`) prints configuration requirements without changing Stripe. `--create` explicitly creates a new endpoint only when one is actually needed. Secrets are obtained from the appropriate Stripe Dashboard, not printed by the command.

## Opt-in Stripe test-mode integration

`phpunit-stripe-sandbox.xml` runs `tests/Sandbox/StripeMembershipSandboxTest.php` against the real Stripe API. It is deliberately excluded from the ordinary review suite. The harness bootstraps the isolated review application with an in-memory SQLite database, fake mail/notifications/events and fake Laravel HTTP/Redis. It parses the local `.env` as data only to obtain the selected account's test secret; normal database, queue, mail and webhook credentials are never imported. It refuses non-test API keys and verifies `balance.livemode === false` before creating fixtures. The SDK uses the membership integration's pinned Basil version.

Run explicitly only with test credentials and network access:

```sh
php -d error_reporting=8191 vendor/bin/phpunit -c phpunit-stripe-sandbox.xml
```

Each case creates its own test clock, customer, subscription, product and monthly/yearly Prices. Only customers created by the test gateway receive that clock. Cleanup deletes that clock's customer/subscription graph and archives its own Prices/product, including after failures; a cleanup failure reports fixture IDs for review. Stripe may retain archived catalog objects and event history. Provider errors are reduced to class/code/parameter/status/request ID, without keys, client secrets or raw payment/contact payloads. The suite performs actual test-mode provider writes, including a test refund, and never uses existing customer IDs.

Coverage includes trial setup (including Stripe's second subscription SetupIntent), paid confirmation and replacement-card retry, duplicate completion, card replacement, scheduled plan changes, cancel/resume, pause/unpause, invoice history/preview, a test-clock trial conversion at the annual-plan boundary, actual charge/refund event replay and unfinished-authentication/decline refusal in both configured accounts. Each replacement has its own signing secret: obtain it from the **Swiss** Dashboard, set `STRIPE_SWISS_WEBHOOK_SECRET` on the server, refresh cached configuration and verify actual delivery before retiring the older endpoint. The US endpoint and signing secret are separate. Keep Swiss API credentials, signing configuration and account access until its active subscriptions and future return-checkout/reconciliation paths have been deliberately addressed; this repair does not migrate or cancel subscriptions across accounts.

When replaying through `stripe events resend`, the Stripe CLI uses its own authenticated account context, independently of Laravel's `--account=swiss` and server API keys. `--live` selects live mode, not the Swiss account. On the current CLI, inspect `stripe login list`, run `stripe switch` and select the Swiss account in live mode before resending a Swiss event to the Swiss destination. If Swiss is not authorized, use `stripe reauth` to add access and then select it. Both the event ID and destination ID must belong to the selected account. A CLI account-selection problem is not a reason to create a second replacement endpoint. See [CLI account selection](https://docs.stripe.com/cli/switch), [authorized accounts](https://docs.stripe.com/cli/login/list) and [event resend](https://docs.stripe.com/cli/events/resend).

The CLI's successful replay response contains the original event, not an individual destination's delivery response. A historical event can retain `api_version: 2020-03-02` because its stored data/version is immutable; that does not establish the new destination's configured version. `pending_webhooks` counts deliveries not yet recorded successful across destinations. Confirm the new destination's actual **Delivered / HTTP 200** status in Event deliveries. See [the Event object's version and pending-delivery fields](https://docs.stripe.com/api/events/object).
