# Shared paid checkout

Implemented locally on October 28, 2026. Merchandise, paid eBooks/eScores and web membership purchases use the same full-screen checkout shell, secure card fields and wallet component. Production activation is separate; this change does not enable live checkout, change server secrets or place a real Printful order.

## Payment and delivery

Customers pay PianoLIT through Stripe. Merchandise payments and Printful fulfillment are separate transactions: after Stripe confirms payment, PianoLIT submits the purchased sync variants to Printful, which charges PianoLIT's configured billing method for production and delivery. This is not a split payment or a payout from Printful.

`ShopCheckout` re-resolves prices and variants on the server, validates the destination, obtains Printful shipping options and a cost estimate, and calculates customer tax with Stripe Tax in live mode. All destinations returned by Printful are offered; the actual products/address must also return an available shipping rate and successful estimate. USD is the supported merchandise currency. A quote lasts 15 minutes. Delivery/tax and digital billing/coupon totals update automatically once required fields are valid and editing has paused for one second; there is no Calculate button. Identical input/change notifications are deduplicated, only one quote request runs at a time, and older responses cannot replace newer address details. Changing the destination clears obsolete delivery options. Closing checkout cancels queued work. Provider failures offer a Try again action without a retry loop. Expired or server-invalidated quotes refresh before payment so the customer can review the updated total; an uncertain payment response never silently starts a replacement payment.

`shop_orders` stores an immutable priced snapshot, encrypted contact/address data and durable Stripe/Printful identities. The browser cannot mark an order paid. A successful PaymentIntent must match the stored order, amount, amount received, currency and live/test mode. The signed webhook and minutely reconciliation recover payments when the browser closes before returning. A lost response reuses the same provider identity; it never starts a replacement charge automatically.

Only a verified, paid production order can create a Printful draft. Fulfillment checks its external ID, sync variants, quantities, destination, currency and estimated cost before confirming it. A cost increase or refunded/disputed payment is held for review. Recovery looks up the stable external ID before creating or confirming anything. Local and test orders cannot reach Printful, even if a real token remains installed. Confirmation can incur a Printful charge; do not use it as a connection test.

Paid digital editions use the same modal without shipping and grant one existing account-owned Purchase after verified payment. Their legacy download formats/endpoints, free/member/owned actions and mobile transaction contracts remain available. Coupons use the shop Stripe account; restricted or incompatible coupons are rejected, and a valid 100% coupon grants delivery without a charge. Digital items are purchased individually and do not enter the physical bag. Existing subscription/account ownership, US/Swiss membership routing and signed membership webhooks stay with the membership billing service.

## Local testing

No `.env` change is required when the existing local membership account already has a `pk_test_` / `sk_test_` pair. The shop can use these test credentials locally, or explicit `SHOP_STRIPE_KEY` / `SHOP_STRIPE_SECRET` test keys. Stripe test payments use simulated shipping and zero sample tax; Printful is disconnected. Offline delivery countries live in `resources/data/shop-checkout-countries.json`, including all 50 US states plus DC and all 13 Canadian provinces/territories. These are sample delivery destinations, not a production shipping-coverage snapshot; live destinations and subdivisions remain authoritative from Printful. State codes follow [USPS](https://pe.usps.com/text/pub28/28apb.htm) and [Canada Post](https://www.canadapost-postescanada.ca/cpc/en/support/articles/addressing-guidelines/symbols-and-abbreviations.page). Arthur requested removal of the test-card instruction banner; sandbox/demo mode and local isolation remain enforced by the server. Use Stripe's public test card `4242 4242 4242 4242`, a future expiry and any three-digit CVC. Test digital purchases stay in the local account and send no purchase email.

Set `SHOP_CHECKOUT_MODE=demo` for offline demonstration without Stripe requests. Missing or live credentials on a local installation also fall back to demo. `Printful::enabled()` is unconditionally false locally, and order confirmation independently requires production, live mode, the explicit fulfillment flag and the matching real store. Sample store ID `0` remains local-only. New products still require manual import; scheduled catalog deletion checks are unchanged.

Apple Pay and Google Pay are actual Stripe Express Checkout buttons, shown only when supported and available. They require HTTPS and registered payment-method domains. Arthur chose to keep Shop and membership development on HTTP on October 28, 2026. HTTP card tests work, but wallet buttons intentionally stay hidden there. The attempted local test-domain registrations were disabled after that decision; no local HTTPS sites or public tunnel were installed. Stripe rejected Apple Pay activation for the reserved `.test` names, so future wallet testing also needs an accepted HTTPS hostname, rather than just a local certificate. Do not bypass a certificate warning.

## Local shipment simulation

Open **Admin → Shop → Orders** at `http://admin.pianolit.test/shop-orders` as a manager.

1. Choose **Create sample order**, or open an already-paid local merchandise test order. The created sample uses fictional customer/product data and makes no Stripe payment.
2. Choose **Simulate shipped**. Customer tracking gains a sample carrier, tracking number, delivery estimate, package contents and tracking history. A shipping-email preview joins the purchase-confirmation preview.
3. Open **View email** or **Plain text** under Customer emails. These use the real editable confirmation/shipping templates. **View customer tracking** opens the normal signed Shop tracking page; the email's package link opens a local signed package page, with no carrier request.
4. Choose **Simulate delivered**, then refresh tracking. Replaying either event exercises duplicate protection; it does not create another package/email or regress Delivered to Shipped. Delivery captures the third email, **Your order arrived!**, once the whole order is delivered. Older delivered local samples can use Replay delivered to capture this preview too.

`LocalShipmentSimulator` and its manager/CSRF-protected admin controller require `APP_ENV=local`, a paid merchandise order in `demo`/`sandbox` mode, reserved store `0`, and no real provider order identity. Environment checks run at request/service time even if routes were cached elsewhere. Live/unpaid/digital/foreign-store orders are rejected. Signed sample-package links are also local-only and order-bound.

The simulator supplies generated event/provider snapshots to the same `ShipmentUpdates` normalization and transactional persistence used after real provider verification. It does **not** call or weaken `/webhooks/printful`, register a Printful callback, use production signing keys, or prove provider-to-server transport. Local outbox rows have `preview` status and no delivery timestamp; `OrderEmails` still refuses delivery outside production and refuses all non-live orders even on a production copy. No mail-provider send or Printful request occurs. Local paid checkouts also capture their confirmation preview; older test orders get it when shipping is simulated. Nothing needs enabling in `.env`, and no new migration or scheduler is required beyond the existing shop/tracking migrations.

## Production rollout

Deploy a committed revision through Git. Do not copy uncommitted application files over tracked server files.

1. Back up the database, then run `2026_10_28_200000_create_shop_orders.php` before serving the new checkout. Existing merchandise/catalog migrations must already be installed. Preserve `APP_KEY`, which encrypts saved addresses.
2. Install a dedicated, matching shop Stripe publishable/secret key pair as server-only `SHOP_STRIPE_KEY` / `SHOP_STRIPE_SECRET`. The shop uses its own Stripe client and API version `2025-03-31.basil`; it does not replace the legacy digital/mobile client or membership account configuration.
3. Create a separate Stripe snapshot-event webhook for `payment_intent.succeeded`, targeting `https://pianolit.com/webhooks/shop-checkout` (the existing webhook route is host-independent). Use the shop Stripe account and store its signing secret as `SHOP_STRIPE_WEBHOOK_SECRET`. Keep existing membership endpoints and their US/Swiss secrets unchanged. Invalid signatures fail closed; no production test bypass exists.
4. Configure Stripe Tax registrations, origin/business settings and applicable product tax codes before activation. Review `config/shop-checkout.php` with the actual products/jurisdictions; the eScore code is the generic electronic-services default. The application records a tax transaction only after payment. Provider tax calculation failure blocks checkout. Sandbox tax is illustrative and does not establish live tax correctness.
5. Replace the current product-read-only Printful token with a store-scoped credential that retains product reads and adds Orders read/write access for the PianoLIT store. Install it in the existing private token file with the same restricted PHP/scheduler read permissions. Configure Printful billing. Never expose the token or verify access by creating/confirming a real order. The old token alone cannot submit orders.
6. Register `shop.pianolit.com` and `my.pianolit.com` as Stripe payment-method domains for every account/mode used there, including the relevant US/Swiss membership accounts. Serve valid HTTPS and enable Apple Pay/Google Pay in Stripe. Test with a compatible browser and configured wallet; buttons are capability-dependent.
7. Set `SHOP_CHECKOUT_ENABLED=true` and `SHOP_CHECKOUT_MODE=live` only after the above setup. Set `PRINTFUL_ORDERS_ENABLED=true` to enable physical checkout and fulfillment; digital paid checkout does not require Printful. Rebuild Laravel's configuration cache and clear compiled views after deployment. Missing shop keys/webhook secrets keep the new checkout unavailable.
8. Ensure `php artisan shop:process-orders` runs every minute under the application identity, with overlap protection. It is registered in `Console/Kernel.php`. The previously installed scoped Printful catalog cron does **not** run this new command, and full production scheduler coverage remains unverified. Add a scoped locked job or confirm/consolidate the existing full scheduler; do not enable unrelated scheduled billing/email jobs blindly.

Membership wallets use the existing verified SetupIntent/subscription flow and existing membership signing secrets. Their availability does not depend on the shop's activation flag. Local membership credential resolution also rejects live keys.

## Operations and limits

Managers use **Shop → Orders** (`admin.shop-orders.*`, `/shop-orders`) to review quotes, paid orders and fulfillment. Regular admins cannot access this directory. Production shows live orders; local shows demo/sandbox orders. Payment preparation, completion and receipts enforce the owning session/account; checkout writes use same-host CSRF, throttling and session blocking. Payment client secrets are stripped from return URLs before receipt HTML renders.

`shop:process-orders` reconciles pending payments from the last seven days and paid orders awaiting delivery, up to 100 per run. It never creates a new payment. Paid merchandise with transient failures can also use **Retry fulfillment** in the order view; it verifies Stripe again and reuses the provider order. `review_required` deliberately stops automatic fulfillment. Review the Stripe payment and Printful draft before resolving any cost/address/payment issue. The application does not automate refunds, cancellations or manual cost approval. Shipment tracking and the three merchandise email types are described below; existing digital purchase confirmations remain independent.

Addresses are encrypted at rest but visible to authorized managers and the payment/fulfillment providers as necessary. This feature introduces no indefinite-retention authorization or automatic unpaid-quote purge. Define retention and account-closure treatment for shop order records before public launch; preserve legally required payment/order history and never delete paid records merely to clear a queue.

## Verification

The isolated review suite covers server prices, expired/changed quotes, ownership, encrypted addresses, digital delivery/coupons, payment proof and mode checks, signed/duplicate webhook handling, lost responses, idempotent fulfillment, review holds and manager permissions. Shared JavaScript checks cover wallet capabilities, setup/payment confirmation, failures/disposal and existing membership behavior. SQLite does not establish production MySQL locking.

Two browser purchases succeeded using real Stripe **test** keys: a sample T-shirt ($28 plus $5 simulated delivery) and a $10 test eBook whose existing download page opened successfully. No real payment, live Printful request/order or purchase email was sent. Desktop/mobile layout checks and production asset compilation are local evidence; eligible-device Apple Pay/Google Pay, live webhook delivery, production cron, tax settings and Printful write permissions remain deployment checks.

## Merchandise emails and customer tracking

Added locally on October 28, 2026. Production `HEAD /webhooks/printful` returned 404 during this change, confirming that the new handler is not deployed there. No live Printful subscription or customer email was created as verification.

There are three merchandise automatic email types, all enabled by default in Administration → Emails, with independent sending switches, HTML/plain-text previews and the existing admin-only preview-send control:

- **Merchandise purchase confirmation:** created once after Stripe payment is verified. Thanks the customer, lists items/options/quantities, delivery/tax/paid total and includes a private order link.
- **Merchandise shipped:** created once per actual package after an authenticated shipment update. Includes its items, carrier/service, tracking number/link, shipped date and provider delivery estimate when available. A split order or replacement package can therefore produce more than one shipping email; duplicate webhook deliveries do not repeat it. A delivered update also evaluates whether the whole order has arrived.

- **Merchandise delivered:** subject and heading **Your order arrived!**, created once per order when Printful reports fulfillment complete and every package is delivered. Includes the order reference, latest reported delivery date, purchased items, private order link and help contact. Split orders wait for the last package. Webhook replay and polling cannot resend it; existing historical delivered orders are not automatically backfilled. The sender waits for pending confirmation/shipping messages and rechecks that the order is still fully delivered.

Editable bodies are `resources/views/emails/shop/orders/confirmed.blade.php`, `shipped.blade.php` and `delivered.blade.php`. The shared existing transactional email layout supplies their logo, typography, button and footer. Admin preview fixtures never use real purchases or private tracking links.

The account menu now has **Track your orders**, opening the absolute main-site `/profile/orders` page. My downloads links to it while retaining its existing digital library. It shows only the signed-in account's paid merchandise orders, eight per page. New accounts do not inherit retired or guest purchases merely by sharing an email address. Guest customers instead keep the private link from their email, which opens a read-only Shop tracking page on any device without signing in or installing another app. Signed links expose order items/totals and shipment data, not contact/address/card/Stripe details. They have private/no-store, no-referrer and noindex headers; signature-bearing requests and the private order history/receipt routes are excluded from website analytics. Treat these links as private bearer credentials. Keep `APP_KEY` stable; rotating it invalidates old signed links as well as encrypted-address access.

### Printful shipment webhook activation

This uses **Printful v2 signed webhooks**, whose shipment event is named `shipment_sent` (the newer counterpart to the diagram's unsigned v1 `package_shipped`), plus `shipment_delivered`. Catalog management and fulfillment creation keep their existing v1 endpoints. The handler at `POST https://pianolit.com/webhooks/printful` verifies `x-pf-webhook-public-key` and the HMAC-SHA256 `x-pf-webhook-signature` over the exact raw body, using the **hex-decoded** one-time secret. Missing/invalid signatures, wrong stores and unpaid/unrelated orders cannot update a customer order. No legacy unsigned compatibility bypass is provided.

After authentication it re-reads the saved external order identity through the server-only API, verifies order/shipment identity and item quantities, and copies bounded tracking fields. V2's shipment endpoint adds delivery status, estimates and recent carrier events to the v1 shipped-package data. Links require safe HTTPS URLs; arbitrary callback data never becomes a carrier link. Duplicate receipts and unique order/package email keys protect retries. Provider failures or a shipment not yet visible through the API return 503 for retry. Delivery updates cannot be overwritten by older shipped notifications.

Before enabling this on the server:

1. Deploy through Git and run `2026_10_28_220000_add_shop_order_tracking.php` after the original shop-order migration. This adds tracking fields, `shop_shipments`, `shop_order_emails` and minimal `printful_webhook_receipts` without raw webhook/customer payloads. This migration is installed locally only. Refresh the configuration cache and clear/rebuild route and compiled-view caches before registering the callback (`config:cache`, `route:clear`, `view:clear`, then the deployment’s usual route caching if used).
2. Verify the real store token has Orders read access and permission to configure webhooks, in addition to the previously required order-write/catalog permissions. The installed product-read-only token is insufficient for the complete workflow. Confirm the public HTTPS callback route is deployed before registering it.
3. Run `php artisan printful:webhooks` to inspect settings without changing them. Run `php artisan printful:webhooks --configure` explicitly to register the two shipment events and save the returned signing key pair in the ignored `storage/app/private/printful-webhook-keys.json` (override its path with `PRINTFUL_WEBHOOK_KEYS_FILE`). The command refuses local execution and refuses to replace a different callback or unrelated event configuration. Its repeated run is a no-op when matching keys/events already exist. Existing settings must be reviewed before replacing them; never overwrite another consumer silently.
4. The signing secret is returned once. The command stages and atomically installs a mode-0600 file, never printing its values. Grant the PHP worker and scheduler identities read access using the established private-directory/read ACL pattern. Atomic replacement creates a new file, so reapply a named PHP read ACL after rotation. Then verify `printful:webhooks` from the actual worker identity. No webhook expiry is requested; the API token's separate expiry/rotation still applies. Printful signing-key changes require the matching local private key file immediately.
5. Run `shop:send-order-emails` every minute and `shop:sync-shipments` every 15 minutes, with overlap protection; both are registered in Kernel. The existing catalog-only and GA-only production crons do not run them. Confirm or add these scoped jobs without blindly enabling unrelated schedules. Order reconciliation remains a separate required minutely command. No new queue worker is required for these two commands.

Read-only shipment polling recovers missed shipping/delivery updates for submitted orders from the last 180 days, in bounded batches with a 45-second request-start budget (one final request may finish later). Tracking and pending email delivery continue even when **new checkout or Printful order confirmation is disabled**. Local modes never contact Printful or send these customer emails. Carrier details are shown as supplied; no arrival date is invented when the provider has none. After 180 days, received valid webhooks still update tracking, but automatic polling stops.

`shop_order_emails` is a durable outbox. Normal sends are claimed once; duplicate callbacks or scheduled runs cannot send them again. Disabled email types are marked suppressed rather than backfilled when enabled later. If SMTP delivery is ambiguous, or a sending process disappears, the message becomes **uncertain** and is held instead of being sent repeatedly. Managers can inspect these states under Shop → Orders and use **Retry email** only after checking that the provider did not deliver it. SMTP cannot provide an absolute exactly-once guarantee across a lost acknowledgement; no such guarantee is claimed. Delivery errors retain only their exception class, without addresses or transport bodies.

Reference: [Printful v2 webhook signing and shipment APIs](https://developers.printful.com/docs/v2-beta/).
